# Exit-side RACK/TLP diagnostic experiment

Production source: `081d214300c1067f17f6c0d02f84a8491f1a7b98`.
Original release SHA-256: `08fcf4020cd3c7274c7abd78fe386b40d2fcf8515082d3475ced324ad109217c`.
Exact gVisor: `v0.0.0-20260530041128-23ef90c42be7`.

This is a diagnostic branch, not a product change or a throughput claim.
No Android, Volga, AES, Legacy, proxy forwarding, buffer, queue, MTU, RTO,
congestion-control, auth, DNS or network configuration changes.

## Source variants

CONTROL is this committed tree. The production constructor and all TCP
options remain byte-identical. Only the existing logging loop and imports
are adjusted; new helpers read existing atomic counters.

RACK-OFF is a detached Linux worktree generated by
`scripts/rack-ab-verify.py`. Its only different tracked file is
`tunnel/tunnel.go`, and its only extra block sets `TCPRecovery(0)`
immediately after `SetTCPBuffers`. Option failure panics with a constant
non-secret message; the process cannot silently start with defaults.

The verifier checks the exact base, an explicit changed-file allowlist,
preservation of constructor/forwarding bytes, all tracked files in both
variants, and byte-for-byte restoration after removing the one block.
The artifact contains the complete per-file SHA-256 manifest and patch.

## Supported API and counter meanings

The pinned gVisor `tcp/protocol.go` defaults recovery to
`tcpip.TCPRACKLossDetection` (1), and its protocol setter/getter support
`*tcpip.TCPRecovery`. `rack.go:shouldSchedulePTO` and
`snd.go:handleRcvdSegment` gate RACK/TLP behavior on that bit.
Zero does not disable SACK or ordinary retransmission/RTO recovery.

Every 3 seconds `[TCP-DIAG]` emits only numeric fields:
recovery mode, current connected/established, retransmits, RTO timeouts,
FastRecovery, SACKRecovery, TLPRecovery, SpuriousRecovery,
SpuriousRTORecovery, FastRetransmit, SlowStartRetransmits, DSACK segments,
segments sent/valid received/invalid received/send errors/connection
failures, and existing link-endpoint packet-in/out counters.

`tunnel_packets` means inbound link-endpoint packets; it is not payload
throughput. Current-connection counters are gauges; other counters are
session-cumulative. Use deltas between recorded window boundaries.
Recovery counters overlap; do not sum them as independent loss events.
There is no separate stack-wide RACK-only counter in this dependency.

## Secret-safe transport readiness

Do not add `--debug`: production verbose logging contains document/auth
and packet-address details. A format-identifier allowlist in `utils.Debugf`
emits constant numeric `[CARRIER-DIAG]` records for transport start, WS
connection/error/reconnect, relay failure and recovered worker panic.
It does not format or inspect arguments. All other debug output remains
disabled. Neither Volga code nor its behavior is modified.

A transport-start event alone is not proof of WS readiness. Require an
actual `ws_connected=1` event after each service switch, with no subsequent
WS error/reconnect, before asking for a phone test.

## Validation and limits

Linux CI validates root and mobile modules for both variants with
`go test ./...`, `go test -race ./...`, `go vet ./...` and
`go build ./...`; race builds use CGO on Linux. Final binary CGO and
GOAMD64 settings follow the hash-verified original release build info.
No production binary is executed during its build-info inspection.

Tests check the actual tunnel constructor's recovery setting in each
variant, unchanged TCP buffer values, exact numeric schema, counter mapping,
non-mutating snapshots and secret-free carrier events.

A new timing-based ACK-stall benchmark is intentionally not treated as
deterministic evidence: the original project has no controlled packet-clock
harness, and wall-clock scheduler/load effects would confound this diagnostic
A/B. No synthetic recovery/speed result is claimed. The pinned option
semantics are established from source and actual constructor/readback tests;
the hypothesis must be evaluated using real paired exit counters and phone
measurements.

## Operational boundaries

Only user2 may switch, via a temporary runtime drop-in. Preserve the original
binary and all argv except the separately named diagnostic executable.
Capture original hash/ExecStart and other-service PID/start times first.
Require active state, exact executable path, expected recovery mode,
WS readiness, a valid numeric snapshot and no secret-bearing logs.
Any failure requires immediate rollback and no phone test.

Phone stays on the ordinary production candidate, user2, Legacy, Optimized.
Initial order: CONTROL then RACK-OFF; one Elisa Tallinn Speedtest each after
15 seconds. Record UTC windows and results separately.
At most one reversed confirmation pair if the initial result is ambiguous.
A speed difference without matching recovery evidence is not causal proof.

Always restore user2's original executable after tests, remove only this
experiment's runtime drop-in, daemon-reload, restart only user2, and verify
original hash, argv, no remaining drop-in, active state and unchanged
other-service PID/start times. No Release, upstream PR, Windows Go execution
or antivirus changes.
